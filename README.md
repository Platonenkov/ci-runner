# ci-runner

Self-hosted раннеры GitHub Actions для приватных репозиториев организации StaticBit-io. Репозиторий описывает
хост целиком: новый сервер настраивается одной командой с ПК администратора, а разворачивается кнопкой в Actions.
Адреса, ключи и токен в репозиторий не попадают: они хранятся в секретах GitHub.

## Как устроено

- На хосте работает `SLOTS` слотов, каждый слот - unit `ci-runner@<N>`.
- Один запуск слота обслуживает один job. Хост получает у GitHub одноразовый JIT-конфиг раннера и запускает
  контейнер из образа `image/`. После job'а контейнер удаляется, а systemd запускает следующий.
- Контейнеры работают под `sysbox-runc`: у каждого слота свой Docker-демон и своя сеть, без `--privileged`.
  Параллельные job'ы не делят порты, сети и compose-проекты.
- Docker-кэш образов слота (`/var/lib/docker`) живёт в томе `ci-<N>-docker` между job'ами. Контейнеры, сети и
  тома прошлого job'а удаляются при старте следующего. Если кэш больше `DOCKER_CACHE_LIMIT_MB`, он очищается.
- Пакеты NuGet (`~/.nuget/packages`) лежат в томе `ci-nuget`, общем для всех слотов хоста, и сохраняются между
  job'ами. Шаг `actions/cache` для NuGet в workflow на этом раннере не нужен: его кэш хранится в Azure Blob Storage,
  до которого у части хостингов низкая скорость. Пропускать его можно условием
  `if: runner.environment == 'github-hosted'`.
- Job дольше `JOB_TIMEOUT_MINUTES` (по умолчанию 120 минут, `config/defaults.env`) раннер завершает сам, и GitHub
  показывает его упавшим. Без этого зависший шаг держит слот до шести часов: столько GitHub ждёт job'а без
  собственного `timeout-minutes`.
- Токен регистрации хранится на хосте в `/etc/ci-runner/token` и в контейнеры не попадает.
- Раз в неделю таймер `ci-runner-rebuild.timer` пересобирает образ с последней версией раннера. GitHub перестаёт
  принимать версию раннера примерно через 30 дней после выхода новой.

## Структура

| Путь | Назначение |
|---|---|
| `config/defaults.env` | Общие настройки: организация, метка, версия Sysbox и значения по умолчанию |
| `image/` | Образ раннера: Ubuntu 24.04, Docker, .NET 9 и 10, Node 24 (и Node 22 и 24 в кэше `setup-node`), `gh`, `shellcheck` и т. п. |
| `host/` | Скрипты и unit'ы хоста, в том числе `bootstrap-remote.sh` для начальной настройки |
| `scripts/` | Команды для ПК администратора, на PowerShell и bash |
| `.github/workflows/deploy.yml` | Деплой и статус хоста из Actions |
| `servers/`, `.local/` | Локальные данные хостов и ключи деплоя; в git только `servers/example.env` |

## Секреты и переменные

Каждый хост - это GitHub Environment с именем хоста (Settings > Environments).

| Где | Имя | Тип | Значение |
|---|---|---|---|
| Окружение | `SSH_HOST` | секрет | Адрес хоста |
| Окружение | `SSH_PRIVATE_KEY` | секрет | Приватный ключ деплоя, `.local/<имя>/deploy_key` |
| Окружение | `SSH_KNOWN_HOSTS` | секрет | Ключи хоста, `.local/<имя>/known_hosts` |
| Окружение | `SLOTS` | переменная | Число слотов |
| Окружение | `SLOT_MEMORY` | переменная | Лимит памяти слота, например `7g` |
| Окружение | `DOCKER_CACHE_LIMIT_MB` | переменная | Предел Docker-кэша слота |
| Репозиторий | `RUNNER_TOKEN` | секрет | Токен регистрации раннеров, общий для всех хостов |

`RUNNER_TOKEN` - fine-grained personal access token:

- Resource owner: `StaticBit-io`;
- Organization permissions: **Self-hosted runners: Read and write**, больше ничего.

Секрет окружения с тем же именем переопределяет секрет репозитория, если хосту нужен свой токен.

## Новый сервер

Требования: Ubuntu 24.04, вход root по SSH (по паролю или ключу) с ПК администратора, OpenSSH-клиент и `gh`,
авторизованный с правом записи в этот репозиторий. Вложенная виртуализация не нужна.

1. Выполнить начальную настройку:

   ```powershell
   ./scripts/bootstrap.ps1 -Name ryzen -Address 203.0.113.10 -Apply
   ```

   ```bash
   scripts/bootstrap.sh --apply ryzen 203.0.113.10
   ```

   Скрипт один раз заходит на хост вашим доступом и:
   1. создаёт отдельный ключ деплоя в `.local/<имя>/` и разрешает его для root;
   2. читает CPU, память, диск и ключи хоста, фиксирует ключи в `.local/<имя>/known_hosts`;
   3. проверяет вход по ключу деплоя и только после этого отключает вход по паролю;
   4. рассчитывает число слотов и пишет `servers/<имя>.env`;
   5. создаёт окружение и задаёт его секреты и переменные (`-Apply`). Без `-Apply` только печатает их список.

   Отключение входа по паролю пропускается флагом `-SkipHarden` (`--skip-harden`).

2. Если `RUNNER_TOKEN` ещё не задан (gh спросит значение со скрытым вводом):

   ```bash
   gh secret set RUNNER_TOKEN -R Platonenkov/ci-runner
   ```

3. Развернуть: Actions > deploy > Run workflow, `server` = имя окружения. Или из консоли:

   ```bash
   gh workflow run deploy.yml -R Platonenkov/ci-runner -f server=ryzen
   ```

   Повторный деплой безопасен: работающие слоты не перезапускаются и берут новый образ со следующим job'ом.

4. Проверить: тот же workflow с `action` = `status`.

## Перевод репозиториев на раннер

Workflow выбирают раннер через переменную репозитория:

```yaml
runs-on: ${{ vars.LINUX_RUNNER || 'ubuntu-latest' }}
```

```powershell
./scripts/use-runner.ps1 -Mode On -Repo glintwild, xrpl-explorer-net
./scripts/use-runner.ps1 -Mode Off -Repo glintwild
```

`Off` удаляет переменную, и job'ы снова идут на GitHub-hosted `ubuntu-latest`. Это откат на случай, если хост
недоступен: job'ы, ожидающие self-hosted раннер, иначе стоят в очереди до 24 часов.

> **Внимание.** Не включайте раннер для публичных репозиториев, в том числе для этого. PR из форка выполнит
> чужой код на хосте, а для публичных репозиториев GitHub-hosted минуты и так бесплатны.

## Переезд на другой сервер

1. Настроить и развернуть новый хост, как описано в разделе «Новый сервер».
2. Убедиться через `status`, что раннеры нового хоста в состоянии `online`.
3. Остановить слоты старого хоста: `ssh root@<старый> "systemctl disable --now 'ci-runner@*'"`.
   Неиспользованные JIT-регистрации GitHub удаляет сам.
4. Удалить окружение старого хоста в Settings > Environments, а также `servers/<имя>.env` и `.local/<имя>/`.

## Деплой без GitHub Actions

Запасной путь с ПК администратора. Он использует `servers/<имя>.env`, который пишет `bootstrap`:

```powershell
./scripts/set-token.ps1 -Server ryzen
./scripts/deploy.ps1 -Server ryzen
./scripts/status.ps1 -Server ryzen
```

Скрипты заходят на хост вашим SSH-доступом, а не ключом деплоя.
